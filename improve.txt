RELIABILITY & ENGINE POLISH
=============================================================

[OPS-1] Rate limiting on execution endpoint
→ Per-user limit: 10 runs/minute via Redis token bucket.
→ Metric Impact: "Engineered a distributed token-bucket rate limiter using Redis to protect the C++ code execution engine from DDoS attacks and resource exhaustion, successfully capping execution requests at 10 req/min per user and ensuring 99.9% platform uptime."
→ Status: NOT STARTED

[OPS-2] Benchmarking & Monitoring CLI Module
→ Problem: Hard to measure exactly how much time/memory our engine optimizations save.
→ Architecture: Separate runner/workload architecture (Google/Atlassian style) tracking Peak Heap, CPU Time, and P99 Latency. Generates markdown reports.
→ Metric Impact: "Architected a FAANG-grade benchmarking CLI that isolates workloads to measure P99 latency and Node.js GC overhead, providing hard data for performance regressions."
→ Status: IN PROGRESS

[ENGINE-3] Compile-Once, Run-Many Architecture
→ Problem: `jobworker.js` spins up a new Docker container and triggers a full `g++`/`javac` compilation for EVERY test case, crippling CPU. Benchmark (`05_sequential_execution.js`) shows this takes 4.65 seconds for just 10 C++ test cases.
→ Architecture: Separate compilation and execution phases. Compile binary once, mount it, and run against N test cases.
→ Metric Impact: "Eliminated redundant Docker compilation cycles by engineering a compile-once-run-many architecture, reducing multi-testcase execution latency from 4.6s to under 1s."
→ Status: NOT STARTED

[ENGINE-4] Zero-Copy Redis Payload Serialization
→ Problem: `jobworker.js` bundles huge `input` and `expected` strings into the final JSON payload and sends it over Redis. Benchmark (`02_redis_serialization.js`) shows this triggers a +40.8MB GC memory spike and blocks the event loop for ~92ms for large IO payloads.
→ Architecture: Strip input/expected from the worker payload and let the frontend zip the `actual/status` response with local state.
→ Metric Impact: "Drastically reduced backend memory allocation by 40MB per execution and reduced Redis pub/sub bandwidth by omitting static test case data from execution payloads."
→ Status: NOT STARTED

[ENGINE-5] Batch Container Execution
→ Problem: Docker spin-up adds ~770ms per test case (`03_engine_execution.js`). Sequential execution wastes resources.
→ Architecture: Spin up Docker once, feed it an array of inputs via standard I/O streams, and get an array of outputs back.
→ Metric Impact: "Bypassed repetitive Docker lifecycle overhead by implementing batched execution processing, improving total evaluation throughput by 300%."
→ Status: NOT STARTED

MISSING FAANG-LEVEL TESTING & BOTTLENECKS
=============================================================

[QA-1] Code Coverage Enforcement
→ Bottleneck: We don't track Code Coverage (Statement, Branch, Function, Line).
→ Improvement: Configure Jest with `--coverage` and strictly enforce a minimum 90% coverage threshold to block bad PRs.

[QA-2] CI/CD Pipeline Integration
→ Bottleneck: Tests are run manually.
→ Improvement: Implement a GitHub Actions workflow (`.github/workflows/test.yml`) to automatically spin up Redis/MongoDB services and run the test pyramid on every PR.

[QA-3] Deep Unit Testing (Controllers & Models)
→ Bottleneck: We tested validators and middlewares, but business logic in controllers (e.g. `submission.controller.js`) and database schema edge-cases (Mongoose constraints) lack isolated unit tests.
→ Improvement: Mock the database and write unit tests for every controller function.

[QA-4] Security Vulnerabilities (Docker Isolation Edge Cases)
→ Bug: Code execution doesn't actively block users from attempting to read `/etc/passwd` or executing reverse shells.
→ Bug: Fork bombs (e.g., in Python via `os.fork()`) could bypass standard limits if `nproc` is not strictly enforced on the Docker container.
→ Improvement: Apply strictly unprivileged user constraints, drop network capabilities (`--network none`), and enforce `--pids-limit` during execution.

[QA-5] WebSocket Disconnect Handling
→ Bottleneck: Real-time WebRTC/Socket.io lacks rigorous heartbeat/disconnect logic if a peer drops mid-execution.
→ Improvement: Implement comprehensive heartbeat (PING/PONG) logic for WebSockets and expand the test suite to simulate network partitions.

[QA-6] Fuzz Testing
→ Bottleneck: The API is only tested with predicted payloads.
→ Improvement: Inject randomized, mutated, and malformed strings (Fuzzing) into the `code` payload to ensure the C++ engine or V8 runtime doesn't panic.

BACKLOGGED FEATURES: Worker Autoscaling & Load Shedding
=============================================================

### 1. The Worker Autoscaler (Scale Up)
We will create a new Node.js daemon (backend/workers/autoscaler.js) that monitors the Redis queue size and dynamically spawns/kills C++ execution workers.
- Trigger: Polls LLEN submissions in Redis every 2 seconds.
- Scale Up: If Queue Length > (Active Workers * 5), it spawns a new jobworker.js process via child_process.fork, up to a MAX_WORKERS limit.
- Scale Down: If the queue is empty and workers are idle for 30 seconds, it gracefully kills excess workers to save RAM.

### 2. Global Capacity Limiter (Server Busy)
If traffic spikes so fast that even the maxed-out autoscaler cannot keep up, the API protects itself from queue exhaustion.
- We will create a new middleware backend/src/middlewares/queueCapacity.middleware.js.
- If the queue exceeds MAX_QUEUE_SIZE (e.g., 50), the API immediately aborts and returns HTTP 503.

### 3. Personal Rate Limiter (Anti-Spam)
- We will implement express-rate-limit backed by Redis to limit individual users to 10 submissions per minute.
