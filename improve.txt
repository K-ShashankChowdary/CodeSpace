TIER 1 — BUGS (fix before anything else)
=============================================================

✅ [BUG-1] Socket not initialized on direct login / silent token refresh
→ Problem: socket.connect() only fires on explicit login. Hard refresh
  while logged in → no socket.id → all room features broken.
→ Fix: Call socket.connect() inside the JWT rehydration flow, not just
  on login click. Guard every socket.emit() with:
    if (!socket.connected) socket.connect()
→ Status: ALREADY FIXED in IDE.jsx.

✅ [BUG-2] Logout does not disconnect user from room
→ Problem: Logout clears JWT but never emits a server disconnect.
  Interviewer dashboard still shows candidate as active after logout.
→ Fix: Before clearing JWT emit:
    socket.emit("leave-room", { roomId, userId })
    socket.disconnect()
  Handle on server: remove user from room state immediately.
→ Status: COMPLETED. Logout now emits leave-room properly.

✅ [BUG-3] Execution Worker Architecture (Decoupled by Design)
→ Note: The C++ execution worker code exists at `backend/workers/jobworker.js` and is intentionally decoupled from `npm run dev`. This allows the worker to be scaled horizontally across multiple instances (e.g., in a separate EC2 cluster) to handle high load without choking the main Express/Socket server. 
→ How to run locally: Open a second terminal and run `npm run worker`.

TIER 3 — CORE INTERVIEW FEATURES (this is the product)
=============================================================

[CORE-1] Collaborative code editor (THE most critical feature)
→ Problem: Currently only one person can edit. In a real interview,
  both interviewer and candidate write in the same editor simultaneously.
  This is the #1 feature CoderPad sells.
→ Fix: Integrate Yjs (CRDT library) for conflict-free collaborative editing.
  npm install yjs y-websocket
  Sync document operations via Socket.io (y-socket.io provider).
  Persist final document state to MongoDB on session end.
  Both cursors visible with name labels (like Google Docs).
→ Done when: Interviewer and candidate in same room → both type
  simultaneously → no conflicts → each sees the other's cursor in <200ms.

[CORE-2] Multi-language support (Python, Java, JavaScript)
→ Problem: Currently only C++. Real interviews are language-agnostic.
  A candidate should never be forced into C++ if they know Python.
→ Fix: Add language selector dropdown in editor.
  Pull Docker images: python:3.12-slim, openjdk:21-slim, node:20-slim.
  Worker selects image + run command based on language field:
    C++:    g++ -O2 -std=c++17 solution.cpp && ./solution
    Python: python3 solution.py
    Java:   javac Solution.java && java Solution
    JS:     node solution.js
  Same exit code → verdict mapping applies to all languages.
→ Done when: Language dropdown works. Python/Java/JS code runs
  correctly and gets right TLE/MLE/RE verdicts.

[CORE-3] Video call (interviewer + candidate, in-browser)
→ Problem: Right now interviewer and candidate need a separate Zoom
  link. CoderPad has video built-in — that's the experience to match.
→ Fix (Option A — faster): Embed a Daily.co or 100ms.live room iframe.
  Free tier covers ~10,000 minutes/month. Zero WebRTC code to write.
  Generate a unique room URL per interview session.
→ Fix (Option B — self-hosted): Implement WebRTC peer-to-peer via
  simple-peer library. Use your Socket.io server as the signaling server.
  More work but no third-party dependency.
  Recommendation: Start with Option A (Daily.co embed), migrate later.
→ Done when: Interview session page has: code editor (left) +
  video panel (right). One link, no Zoom needed.

[CORE-4] Interview session management
→ Problem: No concept of a structured "interview session" with a
  candidate. Current "Host Room" is for classrooms, not interviews.
→ Fix: New session model in MongoDB:
  {
    sessionId, interviewerId, candidateEmail,
    scheduledAt, duration (90min default),
    problem(s), status (pending/active/completed),
    recordingUrl (future), verdict (hired/rejected/maybe)
  }
  Interviewer creates session → gets shareable link → sends to candidate.
  Candidate clicks link → joins without needing to create an account.
  Session auto-ends after duration. Final code snapshot saved.
→ Done when: Interviewer creates session → shares link → candidate
  joins as guest → session auto-saves code on end.

[CORE-5] Problem bank with 1-Click Import & Custom Problems
→ Problem: No problem library exists. Interviewers paste the question
  in chat manually, which is unprofessional.
→ Fix: Problem model in MongoDB:
  { title, description, examples, constraints, difficulty, tags,
    testCases: [{ input, expectedOutput }], solutionTemplate (per language) }
  Interviewer can:
   1. Pick from curated bank
   2. Paste a LeetCode or Codeforces URL (Backend scrapes/imports the problem text + sample test cases automatically)
   3. Create a custom problem from scratch
  Problem shown in left panel, editor on right (standard interview layout).
  Hidden test cases — candidate can't see expected output.
→ Done when: Interviewer can import a problem via URL, pick from bank, or create a custom one, and the candidate sees the description panel.

[CORE-6] Run against test cases during interview (not just free-run)
→ Problem: Currently users run code with custom input only.
  In a real interview, code should be tested against actual test cases
  to give the candidate real feedback (like LC's "Run" button).
→ Fix: Two buttons:
  "Run" → execute against sample test cases, show input/output (fast feedback)
  "Submit" → execute against all hidden test cases, show pass/fail count
  Verdict: "Passed 4/5 test cases. Failed on: [input shown]"
→ Done when: Run button shows sample case results. Submit button
  shows full verdict with failing test case details.

[CORE-7] Guest Auth Flow (Frictionless Onboarding)
→ Problem: Candidates currently have to create an account with email/password to join a session. This is too much friction for an interview.
→ Fix: Add a `guestJoinSession` endpoint in `user.controller.js`.
  When a candidate enters their Name + Session Code on the landing page, generate a temporary JWT scoped strictly to that session.
→ Done when: A candidate can join an active interview session in under 3 seconds without a password.

DOCS — README must be updated to reflect interview platform pivot
=============================================================

[DOCS-1] HLD + Architecture decisions in README
→ Problem: Current README describes CodeSpace as a 'classroom tool'.
  After the pivot to an interview platform, the README is out of date
  and doesn't explain WHY the technical choices were made.
→ What to write (in this order):

  1. New positioning (update header)
     "Free, open-source technical interview platform. Run coding interviews
     without paying $50/seat/month. Real-time collaborative editor,
     built-in video, multi-language execution."

  2. System Architecture Diagram (Mermaid) — already in README, update it
     Add: Interviewer → creates session → shareable link → Candidate joins
     → Yjs CRDT syncs editor state → both submit code → execution engine
     → verdict via Socket.io → interviewer sees result in real-time

  3. Key Design Decisions

     Decision 1 — Why Docker with cgroups flags vs raw Linux primitives?
     → "LeetCode uses raw cgroups + seccomp + namespaces (no Docker) for
       minimum latency. We use Docker with --memory=256m, --network none,
       --pids-limit=64 which internally uses the same kernel primitives.
       Docker adds ~800ms cold start but eliminates the complexity of
       writing raw clone()/seccomp() syscalls. Acceptable tradeoff for
       an interview platform where execution is not the bottleneck."

     Decision 2 — Why exit code mapping for verdicts (not stdout parsing)?
     → "SIGSEGV=139, SIGABRT=134, SIGFPE=136, TLE=124, MLE=137.
       Reading the OS exit code is the same mechanism the Linux kernel
       and real judges (Codeforces, LeetCode) use. Parsing stdout for
       error strings is brittle — a user's code could print 'error:'
       and fool the judge. Exit codes cannot be faked by user code."

     Decision 3 — Why Upstash Redis (serverless) vs self-hosted Redis?
     → "Self-hosted Redis on EC2 requires managing persistence, replication,
       and memory tuning. Upstash is serverless Redis — zero ops, free tier,
       connection-pooling built-in. For a queue that handles bursts of
       submissions but is idle most of the time, pay-per-request pricing
       is far cheaper than a dedicated instance."

     Decision 4 — Why Socket.io over raw WebSocket?
     → "Raw WebSocket has no reconnection logic, no room/namespace concept,
       and no fallback to HTTP long-polling. Socket.io gives: automatic
       reconnect, pub/sub rooms (interview sessions), and HTTP polling
       fallback for corporate networks that block WS. The overhead (~2KB
       client bundle) is negligible for an interview tool."

     Decision 5 — Why Nginx for WebSocket upgrades?
     → "AWS EC2 doesn't natively handle WebSocket upgrades. Nginx
       intercepts the Socket.io HTTP polling handshake and injects
       'Connection: Upgrade' + 'Upgrade: websocket' headers, converting
       it to a persistent wss:// tunnel. Without this, Socket.io falls
       back to HTTP polling — 3-5x more latency, kills the real-time feel."

     Decision 6 — Why Yjs (CRDT) for collaborative editing? (planned)
     → "Operational Transforms (OT, used by Google Docs) require a central
       server to serialize all operations. CRDTs (Conflict-free Replicated
       Data Types) allow peers to merge edits locally without coordination.
       Yjs is the most mature JS CRDT library, supports CodeMirror/Monaco
       bindings, and syncs over any transport (Socket.io in our case)."

  4. Why this beats the current alternative (Zoom + Google Docs)
     → No code execution | No syntax highlighting | No real-time verdict
     → Candidate must share screen | Interviewer can't run the code
     → CodeSpace: single link, both edit, both see verdict, no plugins needed

TIER 4 — ARCHITECTURAL AUDIT FINDINGS (Code Quality)
=============================================================

✅ [BUG-8] Missing WebSocket Error Boundaries
→ Problem: `socketService.js` makes asynchronous database calls (`await Room.findOne()`) inside the `socket.on("join-room")` event without a `try/catch` block. If the MongoDB query fails, the promise rejection is unhandled and can crash the WebSocket service.
→ Status: COMPLETED. Async handlers safely wrapped.

✅ [PERF-6] Synchronous File I/O in Worker
→ Problem: `jobworker.js` uses synchronous methods (`fs.existsSync`, `fs.writeFileSync`, `fs.unlinkSync`) inside `runCpp()`. Because Node is single-threaded, these blocking operations freeze the event loop, preventing the worker from picking up new jobs from Redis simultaneously.
→ Status: COMPLETED. Refactored to `fs.promises`.

[PERF-7] Redundant N+1 Queries on Registration
→ Problem: `user.controller.js` executes 4 sequential database queries for a single user registration (`User.create()`, followed by `User.findById()`, then another `findById` inside token generation, and finally a `.save()`).
→ Fix: Refactor the controller and the token generation methods to operate on the active Mongoose document in memory without refetching from the database.

✅ [PERF-8] Aggressive N+1 Polling vs WebSockets
→ Problem: `IDE.jsx` aggressively polls the backend every 1.5s via HTTP (`api.get('/submissions/status')`) while code is executing, triggering repeated `Submission.findById()` queries.
→ Status: COMPLETED. Replaced with Redis Pub/Sub.

[CLEAN-3] Unnecessary DB Query in Loop
→ Problem: `room.controller.js` runs `await Room.findOne()` inside a loop to randomly generate a unique room code.
→ Fix: This creates sequential network bottlenecks. Use a robust unique ID generator (like `nanoid` or `uuid`) and rely on MongoDB's unique index constraint (`catch (err.code === 11000)`) instead of checking-before-inserting.
